# legal-rag-lab

> 法律合同条款 **RAG 检索与风险问答**系统：中文法律分词 → **BM25 + 稀疏向量混合检索（RRF 融合）** → 领域特征重排 → **带引用溯源**的抽取式回答 → **敢说"没找到"的拒答** → 合同风险规则引擎
> **Python 3 标准库零依赖** · **前端单页零依赖** · **自带 40 题评测集** · **召回 / MRR / 拒答准确率全部量化**

它不是一个"调个大模型 API 就完事"的 RAG demo，而是把**企业法律 AI 产品真正难的那几件事**各做一遍并给出数字：
检索单元怎么切、中文法律术语怎么分词、没有大模型时怎么保证每句话都能指回原文、
**合同里没写的东西系统敢不敢说"没找到"**、以及这些效果到底怎么度量。

---

## 一、为什么是"法律 + RAG"这个组合

法律场景对 RAG 的要求和普通问答**不一样**，这三条决定了整个项目的设计：

| 普通问答 | 法律合同问答 | 本项目的对应做法 |
|---|---|---|
| 答得流畅就行 | **每句话必须能指回"第几条"** | 检索单元是**条款**而不是文档；答案与引用都由原文抽取，引用在代码层回填并校验 |
| 模型自由发挥 | **不能引入条文以外的知识** | 默认**抽取式**回答（不依赖大模型）；接大模型时也强制 JSON 输出 + 引用校验，编造的条款号一律剔除 |
| 答不出来就猜 | **没写的东西必须敢说"没找到"** | 显式**拒答**机制 + 在评测集上**标定**出来的阈值（不是拍脑袋定的） |
| 效果"感觉还行" | **效果必须能度量** | 自带 40 题标注评测集：recall@k / hit@k / MRR / nDCG / **拒答准确率** / 引用关键词命中率 |

## 二、快速开始

```bash
# 零依赖：不用装任何东西（Python 3.8+）
python -m legalrag --help

# ① 建索引（4 份示例合同 / 109 条条款 / 123 个检索子块）
python -m legalrag build

# ② 检索条款（带 <em> 高亮与"为什么排在这里"）
python -m legalrag search "预付款是多少" -k 3

# ③ RAG 问答（带引用 + 风险提示）
python -m legalrag ask "预付款是多少？"
python -m legalrag ask "合同里约定了股权比例吗？"      # ← 会拒答

# ④ 风险体检（按等级汇总，每条风险都给原文证据）
python -m legalrag audit

# ⑤ 跑评测（含拒答阈值标定）
python -m legalrag eval --calibrate

# ⑥ 起 Web 服务：前端单页 + REST API
python -m legalrag serve --port 8080     # 浏览器打开 http://127.0.0.1:8080/
```

### 前端（`web/`，单页零依赖）

搜索框 + 合同筛选 + 「检索条款 / 提问」双模式；检索结果卡片带高亮与相关度分解；
问答结果带**可点击的引用卡片**（点开看条款原文）、**风险提示条**（按等级着色）、置信度条；
拒答时给专门的提示样式而不是空白页；每条结果可 👍/👎 反馈（落库 SQLite）。

## 三、实测结果（`python -m legalrag eval --calibrate`）

> 语料：4 份合成示例合同（采购 / 技术服务 / 劳动 / NDA）共 **109 条条款**；评测集 **40 题**（34 题应检索到、6 题应拒答）。

| 指标 | 结果 | 说明 |
|---|---|---|
| **recall@5** | **0.8382** | 该找到的条款有多少进了前 5 |
| **hit@5** | **0.9118** | 前 5 条里至少有一条相关的比例（比 precision 好读） |
| **MRR** | **0.6225** | 第一个正确结果的平均排名倒数 |
| **nDCG@5** | **0.6444** | 考虑排名位置的排序质量 |
| **拒答准确率** | **0.9500** | 6 道应拒答命中 4 道 + 34 道可答题**零误拒**（漏拒 2 / 误拒 0） |
| **引用关键词命中率** | **0.7412** | 答案/引用里包含期望金额与期限的比例 |
| **平均问答耗时** | **0.9 ms** | 纯倒排 + 稀疏向量，单机、无大模型 |
| **风险规则 recall / precision** | **0.8667 / 0.7027** | 对人工标注的 30 条风险条款：命中 26 条、漏 4 条、误报 11 条 |

> ⚠️ precision@5 = 0.2059 看着低，但**标注粒度是每题的 1~3 条、k=5，理论上限就是 ~0.2** ——
> 单看它会误判效果，所以同时给出 hit@5。这也是"选指标要选对"的一个实例。

> 📌 **preference 说明**：拒答准确率 0.95 是在**指定合同范围**下的结果；不指定范围（全局检索）时是 4/6。
> 差距来自"问题里混了 1 个语料完全不存在的概念 + 3 个常见词"这种灰区情形，见 §七 边界。

## 四、模块地图

```
legalrag/
  tokenize.py  中文法律分词：术语词典 + 最大正向匹配 + 二元组兜底 + 数值/百分比保留 + 同义词扩展
               ★ 两套分词：query_tokens（检索用，高召回） / tokenize_strict（判置信度用，高精确）
  corpus.py    语料加载与**条款级**切分；长条款再切子块（检索用子块、引用回条款）
  index.py     倒排索引 + BM25 + 稀疏 TF-IDF 向量 + **RRF 混合融合**；子块→条款 max-pooling；
               置信度 = IDF 加权覆盖度 + BM25 饱和 − 关键信息缺失惩罚；LRU 缓存（进出都隔离）
  rerank.py    领域特征重排：覆盖率 / 连续短语 / **查询里的条款号** / 标题命中 / 长度惩罚，
               每项特征都可单独打印（"为什么排第一"必须能解释）
  risk.py      合同风险规则引擎：**规则是数据不是代码**；patterns(OR) + require_all(AND) + 多单位数值
  prompts.py   Prompt 模板 + few-shot + **结构化输出校验** + **提示注入防护**
  answer.py    答案合成：默认**抽取式**（每句来自原文、可单测），大模型可插拔 + 失败自动降级；
               **合同范围推断**（防跨合同拼接引用）
  store.py     SQLite：条款 / 查询日志 / 用户反馈（WAL + 单事务批写 + **跨线程安全**）
  api.py       应用装配 + REST 路由与参数校验（与 HTTP 解耦，可纯单测）
  server.py    HTTP 服务 + 前端静态托管（**防路径穿越**）+ 优雅停机（**绕开 server_bind 的反向 DNS**）
  eval.py      recall@k / precision@k / hit@k / MRR / nDCG / 拒答准确率 / 引用命中率 + **阈值标定**
             + **风险规则对人工标注的 recall/precision**
  cli.py       命令行：build / search / ask / audit / eval / serve / stats
web/           单页前端（原生 JS，无构建、无 CDN）
data/          4 份合成示例合同 + 评测集
```

## 五、几个关键设计（面试会问的就是这些）

### 5.1 为什么检索单元是"条款 + 子块"，而不是整份合同

整份合同进索引，检索出来是一整篇，答案只能说"合同里提到过付款"——**说不出"第 3.2 条"**。
法律场景里"哪一条"比"大概意思"重要得多。所以：**检索单元是条款**，条款号跟着走；
超过 80 字的长条款再切成句子级子块参与打分（否则关键词被长文本稀释），
但**同一条款的多个子块取最高分**（max-pooling）后归并回条款 —— 用户要的是"第 3.2 条"，不是"第 3.2 条的第 2 句"。

### 5.2 为什么 BM25 和向量要"融合"而不是"加权求和"

BM25 擅长关键词、向量擅长近义，两者互补。但**它们的分数尺度不可比**：
BM25 是无上界的正数、余弦在 0~1，直接相加等于让 BM25 主导。
所以用 **RRF（Reciprocal Rank Fusion）**：只看名次不看分数 ——
`RRF(d) = Σ 1/(60 + rank_r(d))`，天然免疫尺度差异。

实测这种融合确实在纠错：搜"预付款比例是多少"时，**BM25 把"培训服务期违约金"排在第 1**
（因为"比例"这个词在它里面很稀有、IDF 高），而向量把它压下去，
融合 + 重排后正确答案"第 3.1 条 预付款"排到了第 1。

### 5.3 拒答阈值是"扫"出来的，不是拍出来的

```
$ python -m legalrag eval --calibrate
拒答阈值标定（在评测集上扫描）：最佳阈值 0.20 → 拒答准确率 0.9500（漏拒 2 / 误拒 0）
```

`eval.calibrate_threshold()` 会扫 0.05~0.80 的候选阈值，按
**"拒答准确率最高 → 误拒最少 → 阈值更保守"** 三级排序选出最优值。
这个数字进的是源码常量 `answer.DEFAULT_THRESHOLD`，并在注释里写明它从哪来。

### 5.4 置信度公式被改了四版 —— 每一版都是被**测出来的失败**逼的

这是这个项目里最值得讲的一段，因为它演示了"没有评测集就只能凭感觉调参"：

| 版本 | 做法 | 实测结果 | 为什么错 |
|---|---|---|---|
| v1 | 命中词数 / 查询词数（**等权**覆盖） | 拒答几乎失效 | 问"约定了股权比例吗"，**合同/约定/比例**到处都是，覆盖率虚高 → **该拒却硬答** |
| v2 | 按 IDF 加权，但**把单字也算进去** | 34 道可答题里**误拒 26 道** | 中文口语提问全是单字噪声（"能/活/做/吗"），它们"语料里没有"被当成关键信息缺失 |
| v3 | 只用多字词 + 缺失惩罚 | 可答题 median 0.932，但**仍有一批归零** | 用了**同义词扩展后**的词去判缺失：语料里不写"首付款"是**预期之内**的，却按缺失扣分 |
| v4 | **检索用扩展词、置信度用 strict 词**；缺失按**同义词组**判定 | **拒答准确率 0.95**（误拒 0） | ✅ 检索要召回、置信度要精确 —— 两件事本来就该用两套词 |

顺带修掉的三个真问题：
- **`质保金` vs 语料里的 `质量保证金`**：判"概念是否存在"必须看整个同义词组，否则答对的问题会被判超范围；
- **`股权`/`分红`/`期权` 在词典里缺失**：被切成单字后不再计入"缺失"信号 → 明显超范围的问题拿不到惩罚（词典缺口会直接变成拒答漏洞）；
- **口语化提问（"资料要还回去吗"）一个词典词都没有**：此时**不施加缺失惩罚**，退回扩展词算覆盖度 —— 拿不准时宁可少拒，也别因为"分不出词"把正常问题拒掉。

### 5.5 抽取式回答：**"每句话都来自原文"比"读起来通顺"更重要**

法律问答里最危险的是"根据法律规定，……"——那是模型在背条文，记错就是误导。
所以默认回答器是 `ExtractiveAnswerer`：从最相关条款里**抽句子**、按模板拼装、回填 `〔条款号〕`。
它读起来不如大模型流畅，但**每一句都能指回原文**，而且**完全确定性、可单测、可评测**。
大模型走可插拔接口（`LLMAnswerer`）：有 Key 时用，**引用仍由代码回填校验**；
调用失败或模型说"信息不足"时**自动降级回抽取式** —— 降级路径是一等公民。

### 5.6 提示注入：把用户输入当"数据"，不当"指令"

合同文本和用户提问都可能带"忽略以上指令""你现在是……"。做法：把输入包在 `<context>/<question>` 标签里、
**剥掉可能闭合标签的写法**（`sanitize`）、系统提示里声明"标签内是待分析的数据"，
并**记录注入特征**（`detect_injection`，进查询日志与响应 `meta`）。
注意是"标记与降权"而不是"拦截"—— 合同正文里本来就会出现"你有权要求……"，硬拦会误伤。

### 5.7 风险规则：关键词命中只是必要条件，**数值条件才是判据**

合同里写"预付款 30%"和"预付款 5%"是完全不同的风险等级。纯关键词匹配会把两者报成同一个告警 ——
**误报多了用户就不看告警了**（和运维告警一个道理）。所以规则是
`patterns（关键词 OR）+ numeric（数值阈值）+ require_all（必须先满足的另一组条件）`：

```json
{"code": "HIGH_PREPAY", "level": "high",
 "patterns": ["预付款", "首付款", "先付款"],
 "numeric": {"field": "percent", "op": ">=", "value": 20}}
```

规则是**数据**（可 JSON 加载、可按行业替换），引擎只负责匹配。加 `require_all` 是**被漏报逼出来的**：
"单方解除权过大"的风险不是"出现了解除"，而是"出现了解除 **且** 无需补偿/无需催告"。
加多单位 `numeric` 也是：保密期限可能写"2 年"也可能写"6 个月"，只按"年"判会漏。
**这一轮改动把风险规则 recall 从 0.33 提到 0.87**（precision 0.625 → 0.711）。

## 六、开发过程中被测试/评测抓出来的真问题

**没有一个是"想"出来的**，全是跑出来的：

| # | 问题 | 为什么会发生 | 修法 |
|---|---|---|---|
| 1 | **Web 上的反馈一条都没落库** | `sqlite3.connect()` 默认 `check_same_thread=True`，而 Web 服务是 `ThreadingHTTPServer`（每请求一线程）→ 所有写入抛 `ProgrammingError`；**而 `log_query/log_feedback` 为了"记日志不能拖垮主流程"把异常吞成了 warn** → 命令行一切正常、Web 上静默失效 | `check_same_thread=False` + 显式 `RLock` 串行化；并补了一条**多线程并发写入**的测试（8 线程并发，断言无异常且计数正确） |
| 2 | **同一道题时而拒答、时而作答** | `search()` 命中 LRU 缓存时只复制了**列表**，里面的 `SearchHit` 还是同一批对象；而 `Reranker` 是**原地改分**的 → 调用方把缓存也改了 → **结果取决于调用顺序**（实测 recall 0.838 ↔ 0.794） | 缓存**只存副本、也只出副本**（进出都隔离）；并加了"交叉调用后指标必须一致"的回归测试 |
| 3 | **置信度被同义词扩展污染** | 用扩展后的词判"关键信息缺失"，语料里不写"首付款"就被扣分 → 问"预付款"也判超范围 | 检索用扩展词、置信度用 **strict 词**；缺失按**同义词组**判定（见 §5.4） |
| 4 | **单字噪声把可答题压到 0 分** | 口语提问里的 能/活/做/吗 被算作关键信息 | 置信度只统计**多字词**（单字区分度太低，承担不了"概念是否存在"的判断） |
| 5 | **风险规则漏报 20/30** | `patterns` 只有 OR、`numeric` 只有单条件，表达不了"解除 且 无需补偿"、"6 个月"这种写法 | 加 `require_all`（AND 组）与多单位 `numeric`；补 `times`（倍数）抽取 → recall 0.33 → 0.87 |
| 6 | **服务"起来了"但端口连不上** | 标准库 `HTTPServer.server_bind()` 顺序是 `bind()` → **`socket.getfqdn()` 反向 DNS** → `listen()`；反向 DNS 一慢，端口"已绑定未监听"，客户端拿到 ECONNREFUSED（**同一坑在另一个项目里让 macOS CI 全红**） | 自定义 `server_bind()` 只做 bind；补一条测试把 `socket.getfqdn` 换成"一调用就炸" |
| 7 | **写文件时把输出目录忘了建** | `eval --out reports/x.json` 时 `reports/` 不存在 → 整次评测白跑 | `os.makedirs(parent, exist_ok=True)` |
| 8 | **词典太薄导致索引被噪声灌满** | 第一版只放"专业术语"，"合同签订后"被切成 合/同/签/订/后，还生成 `同签`/`订后`/`方向` 这类垃圾二元组 | 补常用语汇 + **二元组只在连续 ≥4 个单字时才生成**（短串生成二元组只会往索引里灌假词） |

## 七、边界（面试必被追问，如实说）

1. **语料是合成的示例合同**：`data/contracts/*.json` 是**工程演示用的虚构文本**（主体、金额、日期全虚构），
   **不是**任何真实合同、**不引用任何真实法律法规条文或判例原文**，更**不构成法律意见**。
   真实语料请用 `tools/import_corpus.py` 自行导入（按"第 X 条"切条）。
2. **检索是"词法级 + 稀疏向量"**：BM25 + TF-IDF 稀疏向量，**不是**神经稠密检索（没有 embedding 模型、
   没有向量库、没有重排大模型）。语义泛化能力有限 —— 换个说法问、跨语言、指代消解都处理不了。
3. **默认回答器是抽取式**：它给出的每句话都来自原文（这是优点），但也**不会改写、不会归纳、
   不会跨条款推理**。接大模型能改善表达，但**引用准确性仍由规则层兜底**。
4. **风险规则不判断立场**：`"管辖约定在甲方所在地"` 对甲方有利、对乙方不利；
   本引擎判断的是"**这条约定值得人工复核**"，**不判断对哪一方不利**（要做立场判断需按 `side` 分别配置规则）。
   这也是 precision 0.71 的主要来源（实测 11 条误报里多数是"方向相反的同类条款"）。
5. **拒答有灰区**：问题里混 1 个语料不存在的概念 + 3 个常见词时可能不拒答
   （指定合同范围时 4/6，全局检索时 4/6；详见 §三的说明）。**误拒 0** 是有意换来的 ——
   宁可漏拒也不要把正常问题拒掉，但这个取向**必须由使用者确认**。
6. **单机、单进程、无鉴权**：没有用户体系、没有权限隔离、没有多租户，
   **没有做任何敏感信息脱敏**（真实合同涉密，上线前必须加）。
   `Access-Control-Allow-Origin: *` 是本地开发用的，生产要改白名单。
7. **性能数字是本机自测**（Windows、109 条条款的小语料）：**不代表大规模语料下的表现**；
   没有做分布式索引、没有分片、没有增量更新（改语料要重建索引）。
8. **评测集只有 40 题、语料只有 109 条**：指标置信区间很宽，**不能外推到真实业务**。
   它的价值在于"有一套能回归的尺子"，而不是"0.84 这个数字本身"。
